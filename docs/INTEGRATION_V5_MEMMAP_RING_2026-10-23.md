# INTEGRATION V5 — memmap2 SPSC ring (Tier 5 IPC ring)

Date: 2026-10-23. Authorised by Richard: "Go for it" (2026-10-23),
following spike V5-004 PASS (`docs/SPIKE_V5_004_MEMMAP2.md`), design
(`docs/DESIGN_MEMMAP2_RING_2026-10-23.md`) and spike V5-005 PASS
(`docs/SPIKE_V5_005_MEMMAP_RING.md`). Mirrors the petgraph/rusqlite
integration pattern: spike first, design second, integrate third,
additive FFI, ABI unchanged, honest empty states.

## What was integrated

- **Dependency:** `memmap2 = "0.9"` in `rich_gang_ai_core/Cargo.toml`
  (resolved to 0.9.12, as spike-verified). Pure Rust over mmap
  syscalls, no C dependencies.
- **Module:** `src/ring_ipc.rs` — the spike 005 protocol ported
  unchanged: 64-byte header (magic `RGRB0001`, capacity, producer-
  owned monotonic head, consumer-owned monotonic tail), length-
  prefixed records that never straddle the data-area end (wrap
  marker `0xFFFF_FFFF` or <4-byte pure padding, both counted in the
  counters), head published last after a SeqCst fence, counters via
  volatile access. The daemon-facing `RingIpc` owns the producer and
  consumer mappings of one ring file behind a single
  `parking_lot::Mutex` (the core's established pattern, cf.
  SqlStore's `Mutex<Connection>`). A full ring is an explicit
  `ring_full` error and nothing is written — no overwrite, no
  drop-oldest. An empty recv is `Ok(None)`.
- **Daemon wiring:** `Daemon.ring` field + `ring()` accessor, built
  in `Daemon::new` from the config (below). An open failure fails
  daemon start — no silent degradation path.

## Config semantics (mirroring "store_path")

- `"ring_path"` (non-empty string) + `"ring_capacity"` (integer,
  power of two, >= 64): ring enabled at that file. Opening
  truncates/creates the file — each daemon start begins a fresh
  ring cycle (the spike's create semantics, stated plainly).
- No `"ring_path"` — the shipped `daemon_config.json` state (it was
  NOT changed) — the ring is **disabled**: state reports
  `"enabled": false`, and send/recv are explicit `ring_disabled`
  errors, never a silent in-memory substitute.
- `"ring_path"` present but `"ring_capacity"` missing or invalid,
  or the path unopenable: `Daemon::new` returns an explicit error
  (`ring_config_invalid` / `ring_open_failed`) and
  `rga_daemon_start` fails — test-asserted. No capacity is ever
  defaulted.

## FFI surface (additive, ABI stays 2)

- `rga_ring_state` -> `{"enabled":bool,"capacity":N,"head":N,
  "tail":N,"pending_bytes":N,"pending_messages":N}` —
  `pending_bytes` is head - tail (record framing and wrap padding
  included, as implemented); `pending_messages` counts whole
  unconsumed messages, computed by walking the records without
  consuming them.
- `rga_ring_send` -> `{"ok":true,"bytes":N}`; full ->
  `{"error":"ring_full"}` (message NOT queued); disabled ->
  `{"error":"ring_disabled"}`.
- `rga_ring_recv` -> `{"found":true,"message":...}` or
  `{"found":false}` — **no `message` field at all** when the ring
  is empty, like `rga_store_get`'s missing-key shape.
- cbindgen header `include/daemon.h` regenerated by the build
  (contains all three `rga_ring_*` declarations).

Dart bindings in `NativeBridge`: `ringState()`, `ringSend()`,
`ringRecv()`, following the existing ownership contract (Rust
strings freed via `rga_string_free`, inputs freed in `finally`).
No Kotlin/JNI bindings and no UI surface yet — same posture as the
rusqlite integration at this step.

## What this does NOT prove

- **Not device-verified.** No APK exists (the `other_tcp` build
  permission blocker is unchanged), so the ring has never run on
  the A16; Android evidence is cross-compile + symbol verification.
- **No shipped consumer yet.** Nothing in the app uses the ring:
  the shipped `daemon_config.json` has no `ring_path` (a booted
  daemon runs with the ring disabled), and choosing the on-device
  file location (app files directory) belongs to the app wiring
  step, as does any UI.
- **No cross-process reader proven.** Producer and consumer are
  two mappings in the daemon's one process — the coherence proven
  by the spikes is same-OS page cache within one process. A second
  process or a Dart-side reader remains unproven.
- **No CRC — crash scope unchanged from the design doc.** A record
  whose head was never published stays invisible; a crash during
  head publication is unhandled. Production traffic needs the
  CRC/commit hardening named in the design before it is trusted.
- "Memory-mapped" names the mechanism only. **No latency or
  throughput was measured**; no "zero-copy" performance claim is
  made, and the existing slot-locked `ring_buffer` is untouched
  and still honestly labelled not-zero-copy.

## ADDENDUM (2026-10-23, later session) — protocol v2: per-record CRC-32

At Richard's directive ("Fixed problems add solutions"), the "No
CRC" gap listed above was closed the same day. Summary (full
protocol record in the v2 update block of
`docs/DESIGN_MEMMAP2_RING_2026-10-23.md`):

- **Protocol v2:** header magic bumped `RGRB0001` -> `RGRB0002`;
  record layout is now [u32 length][payload][u32 CRC-32/IEEE],
  CRC computed over the length bytes + payload, written by the
  producer before head publication (same head-published-last
  discipline). Record overhead is 8 bytes (was 4). CRC-32 is a
  small table-driven implementation inside `ring_ipc.rs` — no new
  external dependency — pinned by unit tests against published
  check vectors (`CRC32("123456789") = 0xCBF43926`, plus empty,
  "abc", and the quick-brown-fox vectors).
- **Old files:** v1 files are rejected with explicit
  `ring_bad_magic`. No migration — rings are transient IPC files
  recreated at every daemon start.
- **Consumer behaviour:** bounds + CRC are validated before
  delivery. Any failure (zero/oversize length, record straddling
  the data-area end, record extending past the published head —
  the torn case — or CRC mismatch) returns an explicit
  `ring_corrupt: offset=<logical tail>` error; at the FFI surface
  this is the `error` value verbatim (no new JSON field was
  added). Bad bytes are never delivered, never skipped, and the
  tail does not advance. `pending_counts` applies the same
  validation and stops counting at the first corrupt record.
- **Tests:** cargo suite is now **78 passed** (74 before + 4 new:
  CRC vectors, flipped-payload-byte -> `ring_corrupt` and nothing
  delivered, torn record (inflated length past head) ->
  `ring_corrupt`, v1 magic rejected). Existing count-sensitive
  tests (wrapper roundtrip head/tail, full-ring capacity, FFI
  roundtrip/full) were updated to the real v2 record math.
- **Artifact:** libdaemon.so rebuilt RELEASE for aarch64 and
  restaged — SHA-256
  `a8c4158137348a0304858b885978212fa4eda65cc27807889872fa8947ab5d76`,
  2,745,488 bytes. **Export count unchanged at 30** — the CRC is
  internal to the ring module; the FFI surface did not change
  shape (the only externally visible difference is the
  `ring_corrupt: offset=N` error string value on a corrupt recv).
  `tools/release_gate.sh --suites` — **PASS, all checks green**
  (freshness at the new SHA, 30 exports, 26 Dart lookups resolve,
  Align 0x4000, ABI 2 == 2, cargo 78 passed, analyze clean,
  flutter test passed).
- **What the CRC does and does not prove** (narrowed crash scope):
  a delivered record's bytes are now proven to be exactly the
  bytes the producer checksummed, and a torn record published by
  a crash is DETECTED as an explicit error instead of delivered
  as garbage. It does not make head publication atomic, says
  nothing about unpublished records (still invisible), and is an
  integrity check, not a MAC. Still not device-verified, still
  no shipped consumer, still no cross-process reader proven.
