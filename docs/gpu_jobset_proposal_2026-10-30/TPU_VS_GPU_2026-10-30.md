# Cloud GPU instead of TPU — proposal note (2026-10-30)

Status: **PROPOSAL ONLY. Nothing here has been applied, provisioned,
built, pushed, or paid for.** Companion file: `gpu_jobset.yaml` in this
same folder. This note makes no cost, quota, availability, latency, or
performance claim.

## 1. What the pasted TPU manifest actually was

Richard's pasted JobSet (`richgang-sovereign-tpu-cluster`) specified:

- 2 replicated jobs, parallelism 4, completions 4
- Node selector `cloud.google.com/gke-tpu-accelerator: tpu-v6e-slice`
  with topology `4x4`, toleration `google.com/tpu`
- Resource `google.com/tpu: "4"` (limits and requests)
- Container image `us-docker.pkg.dev/rich-gang-ai/daemons/sovereign-core:latest`
- Checkpoint volume via CSI driver `checkpoint.gke.io`, with volume
  attribute `checkpointConfiguration: tpu-checkpoint-config`

None of that exists on record: no GCP project, no quota, no GKE cluster,
no such image, no checkpoint bucket, and no checkpoint configuration.
The manifest was never applied, and the TPU topology / checkpoint driver
are TPU-specific concepts, not transferable facts about this daemon.

## 2. What changes, TPU -> GPU

| Item | Pasted TPU manifest | GPU proposal (`gpu_jobset.yaml`) |
|---|---|---|
| Accelerator resource | `google.com/tpu: "4"` | `nvidia.com/gpu: "REPLACE_WITH_GPU_COUNT_PER_POD"` (placeholder, not a chosen count) |
| Node selector | `cloud.google.com/gke-tpu-accelerator: tpu-v6e-slice` + topology `4x4` | `cloud.google.com/gke-accelerator: REPLACE_WITH_GPU_TYPE` (no GPU type chosen; no topology equivalent — GPU scaling is node count x GPUs-per-node, not a TPU slice topology) |
| Toleration | `google.com/tpu` | `nvidia.com/gpu` (to be verified against the real node pool's taints) |
| Container image | `us-docker.pkg.dev/rich-gang-ai/daemons/sovereign-core:latest` (does not exist) | `us-docker.pkg.dev/REPLACE_WITH_GCP_PROJECT/daemons/sovereign-core:REPLACE_WITH_TAG` (placeholder; `:latest` deliberately dropped — an unpinned tag is not a reproducible deployment) |
| Checkpointing | CSI driver `checkpoint.gke.io` + `tpu-checkpoint-config` (Multi-Tier Checkpointing) | **Removed, not replaced.** That driver does not apply to GPU nodes. The proposal keeps only a placeholder PersistentVolumeClaim (`REPLACE_WITH_CHECKPOINT_PVC`) and a mount path. Durable checkpointing on GPU must be designed separately. |
| Driver stack | TPU runtime / TPU VM image | NVIDIA driver + CUDA version on the node pool, matched by the daemon image. Neither is specified here. |

What stays the same: the JobSet shape only — replicated jobs, the
mirrored 2 / 4 / 4 counts (carried over, not sized), the container name
`sovereign-daemon`, and the idea of a checkpoint mount point. Everything
that would make it run is still missing.

## 3. What stays unproven either way

Swapping TPU for GPU proves nothing about the daemon itself:

- **No daemon image.** The verified Rust core has no GPU code, no CUDA
  code, and no model. The isolated Tokio spike (`spikes/v5_007_tokio_sovereign_kernel/`)
  routes commands and shuts down cleanly, but its inference reply is an
  explicit `no_inference_provider` error — no model is executed.
- **No cluster, no quota, no region, no node pool.** GPU type, GPUs per
  pod, replicas, region, and driver version are all undecided.
- **No checkpoint/resume path.** The daemon has no checkpoint format,
  no periodic state dump, and no resume logic. A volume mount is not
  checkpointing.
- **No telemetry transport.** The Rust kernel's `ClusterTelemetryBroadcast`
  is an in-memory receipt only; nothing is sent to any cluster, TPU or
  GPU. A JobSet does not create a telemetry path.
- **No model, no inference provider, no latency measurement.** Nothing
  in this proposal measures or claims any of these.

## 4. Posture conflict: $0 / air-gapped vs. cloud GPU

The same blueprint that pasted the TPU manifest also claims zero-cloud
dependency and $0.00 operating overhead. A cloud GPU cluster contradicts
both:

- It is a billed service. No price is stated here because no GPU type,
  count, region, or runtime has been chosen — any price would be invented.
- Workloads sent to it leave the local device, so the air-gapped /
  on-device posture no longer holds for those workloads.
- Data, model files, and checkpoint state would live in cloud storage
  (bucket undecided), with access and retention to be decided separately.

This proposal does not resolve that conflict. It only records it so the
choice is explicit: local-first on-device, or billed cloud GPU, per
workload — not both at once by assertion.

## 5. Open decisions for Richard (none made by this proposal)

1. **Provider:** GCP is implied by the GKE shape of the pasted manifest,
   but is not confirmed. Any other cloud changes the node selectors,
   driver install, and storage design.
2. **GPU type and count:** GPU model, GPUs per pod, replica count, and
   region. No recommendation is made here without a workload and a
   budget.
3. **Budget and spend cap:** a hard budget, and who approves spend, before
   any cluster is created. No spend is authorised by this proposal.
4. **Daemon image:** what the image actually contains (Rust core build,
   driver/CUDA base, model — if any, and if so which model, chosen
   separately). No image is built by this proposal.
5. **Checkpoint design:** storage (bucket / volume), checkpoint format,
   frequency, and resume logic — or an explicit decision that
   checkpointing is out of scope for a first GPU run.
6. **Posture decision:** which workloads, if any, are allowed to leave
   the device, and what data they may carry.

## 6. What a real next step would look like (not done here)

Only after decisions 1–3 and 6 above: provision a cluster, install the
JobSet controller and GPU drivers, build and push a real daemon image
with a pinned tag, design and test checkpointing, and only then apply a
filled-in (placeholder-free) manifest. Each of those is a separate
decision and a separate action; none of them is authorised or performed
by writing this proposal.
